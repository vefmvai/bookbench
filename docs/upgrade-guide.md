## Две команды обновления

BookBench разделяет обновление **кода плагина** и обновление **тел субагентов в твоей книге**. Это разные операции, делаются разными командами, имеют разные гарантии.

### `/plugin update bookbench`

Стандартная команда Claude Code. Обновляет код плагина в `${CLAUDE_PLUGIN_ROOT}` до последней релизной версии.

```
> /plugin update bookbench
🤖 Найдена новая версия: 0.1.3 (текущая 0.1.0)
🤖 Скачиваю с github.com/vefmvai/bookbench/releases/v0.1.3...
🤖 Заменяю ${CLAUDE_PLUGIN_ROOT}.
✅ BookBench обновлён до 0.1.3.
```

После этой команды:

- `${CLAUDE_PLUGIN_ROOT}` — заменён целиком (новая версия кода плагина).
- `${CLAUDE_PLUGIN_DATA}` — **переживает** обновление (гарантия Anthropic). Реестр книг, настройки, история evolver — на месте.
- Все папки книг (`.book/`) — **не трогаются** (гарантия архитектуры BookBench, `WF-04`).

Это значит: после `/plugin update bookbench` твои существующие книги **продолжают работать на той версии плагина, на которой они стартовали**. Это сознательное решение (см. ниже).

### `/book:update`

Опциональная команда **внутри папки книги**. Делает 3-way merge новых тел субагентов и hook-скрипта из обновлённого `${CLAUDE_PLUGIN_ROOT}` в твою книгу.

```
$ cd my-book
$ claude
> /book:update
🤖 [book-coordinator] Сравниваю шаблоны плагина с локальными копиями.
   ├─ .book/.claude/agents/book-coordinator.md — без изменений
   ├─ .book/.claude/agents/book-strategist.md — изменён в плагине, нужен merge
   ├─ .book/.claude/agents/book-writer.md — изменён в плагине, нужен merge
   ├─ .book/.claude/agents/book-factchecker.md — без изменений
   ├─ .book/.claude/agents/book-editor.md — без изменений
   ├─ .book/.claude/agents/book-marketer.md — изменён в плагине, нужен merge
   ├─ .book/.claude/agents/book-doc-classifier.md — без изменений
   ├─ .book/.claude/agents/book-doc-synthesizer.md — без изменений
   ├─ .book/.claude/agents/book-tuner.md — без изменений
   └─ .book/.hooks/anti-ai-cliche-lint.sh — изменён в плагине, нужен merge

   Создаю бэкап в .book/.backup/2026-05-08-1432/.

✋ Файл 1/4: book-strategist.md
   3-way merge:
   - старый шаблон: 247 строк (соответствует версии 0.1.0)
   - новый шаблон: 256 строк (версия 0.1.3)
   - локальная копия: 247 строк (без правок автора)

   Diff: [...]

   (a) применить новый шаблон полностью
   (b) применить новый шаблон с моими изменениями (если были)
   (c) пропустить (оставить локальный)
   (d) показать full diff
📝 a
🤖 ✅ book-strategist.md обновлён.

✋ Файл 2/4: book-writer.md
   3-way merge:
   - старый шаблон: 312 строк
   - новый шаблон: 318 строк
   - локальная копия: 315 строк (3 правки автора в гайдлайн-секции)

   Diff: [...]

   (a) применить новый шаблон полностью (теряет правки автора)
   (b) применить новый шаблон с моими изменениями (мерж) ← рекомендуется
   (c) пропустить
📝 b
🤖 ✅ book-writer.md обновлён с сохранением правок автора.

(...)

🤖 ✅ /book:update завершён.
   Бэкап: .book/.backup/2026-05-08-1432/
   Запись в .book/UPDATE-LOG.md (UL-2026-05-08-1).
```

После этой команды:

- `.book/.claude/agents/<role>.md` — обновлены (с твоим подтверждением).
- `.book/.hooks/anti-ai-cliche-lint.sh` — обновлён (с подтверждением).
- Бэкап в `.book/.backup/<timestamp>/`.
- Запись в `.book/UPDATE-LOG.md` (что и когда обновлено).

## Что не трогается

Ни `/plugin update`, ни `/book:update` не трогают:

### `.book/agent-guidelines/<role>/`

Твои гайдлайны — индивидуальность книги. Никогда не обновляются автоматически. Это `D-15` (Universal Body + Local Guidelines).

### `.book/context/`

Факты о книге: `parameters.md` (P-01, P-02, ...), `voice-profile.md`, `glossary.md`, `red-thread-keywords.md`, `cross-references.md`. Контент книги — собственность автора.

### `.book/chapters/`

Все главы в любом виде: `spec.md`, `draft.md`, `factcheck.md`, `edited.md`, `marketing.md`, `summary.md`. Это твой текст.

### `.book/agent-memory/<role>/MEMORY.md`

Реестры уникальности (использованные примеры, метафоры, концепции). Twin к `.book/.claude/agent-memory/`.

### `.book/.claude/agent-memory/<role>/`

Реальные `memory: project` Claude Code.

### Логи

`TUNING-LOG.md`, `REJECTIONS-LOG.md`, `UPDATE-LOG.md` — append-only, никогда не перезаписываются.

### `.book/intel/`, `.book/debug/`, `.book/inputs/`, `.book/final/`

Импорт, debug-сессии, исходники автора, финальная книга.

### `.book/config.yaml` и `.book/workflow.md`

Конфигурация книги. Ни одно обновление их не перезаписывает; правит автор или `/book:tune apply`. См. также раздел [Миграции workflow](#миграции-workflow) ниже.

## Чек-лист апгрейда

Перед запуском `/book:update`:

1. **Сделай git commit** (если используешь git для книги). Бэкап `.book/.backup/` создаётся автоматически, но git-коммит — дополнительная страховка.
2. **Закрой текущую главу**, если в работе — `/book:status` должен показывать «глава X завершена» или «главы Y не начаты», не «фаза 3 в процессе».
3. **Запусти `/book:doctor`** — нет ли каких-то предупреждений.

Запуск:

4. `/plugin update bookbench` — обновляешь код плагина (если ещё не обновил).
5. В каждой книге, которую хочешь обновить: `cd <book>` → `/book:update`.
6. Просматривай diff'ы внимательно — особенно для файлов с `(локальная копия с N правками автора)`.

После:

7. `/book:doctor` — проверь, что всё на месте.
8. Запусти простую команду (например, `/book:status`) — убедись, что субагенты отвечают.
9. Если есть открытая глава — `/book:write-chapter:edit <N>` (только редактор) на проверочной главе — посмотри, не сломалось ли поведение.

Если что-то не так — см. [Откат](#откат) ниже.

## Откат

### Если `/book:update` сломал что-то

Бэкап создан автоматически перед обновлением:

```
.book/.backup/2026-05-08-1432/
├── agents/
│   ├── book-coordinator.md
│   ├── book-strategist.md
│   └── ...
└── .hooks/
    └── anti-ai-cliche-lint.sh
```

Откат — ручное копирование:

```bash
$ cd my-book
$ cp -r .book/.backup/2026-05-08-1432/agents/* .book/.claude/agents/
$ cp .book/.backup/2026-05-08-1432/.hooks/* .book/.hooks/
$ chmod +x .book/.hooks/*.sh
```

Запиши откат в `UPDATE-LOG.md` (вручную, как комментарий — для истории):

```markdown
## UL-2026-05-08-2 (manual rollback)
Откатил `/book:update` от UL-2026-05-08-1 — выявлен баг в book-writer.md.
Восстановлены файлы из .backup/2026-05-08-1432/.
```

### Если `/plugin update bookbench` сломал что-то

Откат версии плагина — через тот же `/plugin install bookbench@<old-version>`:

```
> /plugin uninstall bookbench --keep-data
> /plugin install bookbench@v0.1.0
```

`--keep-data` сохранит `${CLAUDE_PLUGIN_DATA}` (реестр книг, настройки). Все папки книг — нетронуты.

### История бэкапов

В `.book/.backup/` хранятся бэкапы всех `/book:update`. По умолчанию — последние 10. Старые автоматически чистятся (можно настроить через `config.yaml > backup.retention_count`).

Если бэкапа нет (например, ты удалил `.backup/` руками) — единственный путь восстановления через `git revert` (если использовал git).

## Развёрнутая книга не получает обновлений автоматически

Это сознательное архитектурное решение `WF-04` в `PROJECT.md`.

### Почему

После `/book:start` папка книги живёт **автономно**. Её workflow.md, agent-guidelines, локальные копии тел субагентов и hook-скрипт **застывают** в той версии плагина, в какой были на момент инициализации.

Причины:

1. **Папка книги — собственность автора** (`D-21`). Плагин не должен в неё лезть без явного запроса.
2. **Книги пишутся годами.** Если плагин с каждым релизом меняет тела субагентов, поведение книги — нестабильно. Автор не понимает, почему писатель внезапно стал писать иначе.
3. **Эволюция плагина — не «исправление ошибок», а «улучшение по опыту других книг».** Ты можешь не хотеть подтягивать чужие наблюдения в свою книгу.
4. **Тестирование релиза — отдельная задача.** Каждый раз накатывать обновления на работающую книгу — риск нарушить рабочий цикл.

### Что записано для диагностики

В `.book/workflow.md` есть номер версии BookBench, на котором книга стартовала:

```yaml
metadata:
  bookbench_version_at_start: "0.1.0"
  workflow_preset: "popular-science"
  initialized_at: "2026-04-10T11:30:00Z"
```

Это **только для диагностики**: если ты приходишь с проблемой, мы (maintainer'ы) понимаем, с какими шаблонами ты работал.

### Что делать, если очень нужны обновления

`/book:update` — ручная процедура, делается **только по явному запросу**. Запускается одним вызовом per книга, с 3-way merge для каждого изменённого файла (см. выше).

Если ты не запускаешь `/book:update` — книга может оставаться на стартовой версии хоть пять лет. Это нормально.

## Миграции workflow

`workflow.md` — это конфиг (DAG из блоков), не язык программирования (`WF-01`). Структурно стабилен между версиями.

### Что может измениться между версиями плагина

- **Каталог блоков** (`blocks-catalog.md`). Новые атомарные блоки или процедуры могут добавляться. Существующие — не удаляются и не переименовываются (это сломало бы существующие книги).
- **Параметры существующих блоков**. Могут добавляться новые опциональные параметры (с дефолтными значениями). Существующие параметры не удаляются.
- **Дефолты пресетов**. Например, в 0.1.3 пресет `popular-science.yaml` может получить более строгий `factcheck_max_iterations` (3 → 5).

### Что НЕ изменится без мажорной версии

- Контракт `chapter-loop` (вход / выход / параметры).
- Структура секций workflow.md (`book_level`, `chapter_loop`, `cross_cutting`, `post_book`).
- Имена и роли 9 субагентов.

### Применение новых дефолтов к существующей книге

`/plugin update bookbench` **не меняет** твой `workflow.md`. Если хочешь подтянуть новые дефолты пресета:

```
> /book:workflow:check
🤖 [book-coordinator] Проверяю workflow.md...
   Текущая версия: 0.1.0 (preset popular-science)
   Доступная версия preset'а: 0.1.3
   Изменения:
   ├─ chapter_loop.params.factcheck_max_iterations: 3 → 5
   └─ chapter_loop.params.target_length.max: 8500 → 9000

✋ Применить новые дефолты? (y/n)
   Бэкап будет создан в .book/.backup/.
   Твои override'ы (если есть) сохранятся.
📝 y
🤖 ✅ workflow.md обновлён.
```

`/book:workflow:check` без подтверждения — статическая валидация workflow.md (полезно после ручных правок).

### Если plugin изменил блок, который ты используешь

Это редкий случай (мажорная версия). Тогда `/book:workflow:check` покажет breaking change и предложит ручную миграцию.

В 0.1 → 0.2 такие случаи будут описаны в CHANGELOG.md в разделе `Breaking changes`. Пока в 0.x.x — гарантируется обратная совместимость workflow.
