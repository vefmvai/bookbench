## Зачем разбивать главу на 5 фаз

Глава нон-фикшн-книги — это пять разных задач, упакованных в один конечный текст:

1. **Решить, что в главе должно быть и в каком порядке** — стратегическая задача. Требует холодной головы и общей картины книги.
2. **Написать прозу с удержанием голоса автора** — творческая задача. Требует погружения в стиль, риск отвлечения на проверку фактов.
3. **Проверить факты** — критическая задача. Требует адверсариальной стойки («не доверяй автору, доверяй источникам»). В одной голове с писателем это работает плохо: автор сосредоточен на стиле и проскакивает факты, фактчекер сосредоточен на фактах и теряет голос.
4. **Подчистить связность и стиль** — редакторская задача. Требует двойного audit-pass анти-ИИ-клише и проверки cohesion с соседними главами.
5. **Упаковать готовое для соцсетей и обложки** — маркетинговая задача. Требует переключения регистра и совершенно другой риторики.

Один универсальный агент пытается всё это делать в одном контекстном окне — и теряет глубину каждой задачи. Команда из пяти специализированных субагентов с собственными `skills:`, `tools:` и `memory: project` решает каждую задачу глубоко, изолированно, с возможностью верификации между фазами.

> **Это не «выбор стиля» — это архитектурное следствие платформенного ограничения** Claude Code (субагент не может вызвать другого субагента), превращённое в преимущество. Изоляция контекстов даёт качество, недостижимое одним «универсальным» агентом.

Полное обоснование 5 фаз (а не 4, как у автора BookBench изначально) — в `tradeoffs-and-decisions.md` этапа 11 проекта.

## Обзор пяти артефактов

Каждая фаза создаёт один файл в `chapters/<NNN>/`. Передача между фазами — через файлы, не через память агентов:

```
chapters/01/
├── spec.md            (от стратега; ТЗ главы)
├── draft.md           (от писателя; черновик)
├── factcheck.md       (от фактчекера; отчёт о проверке фактов)
├── edited.md          (от редактора; финальная глава)
├── marketing.md       (от маркетолога; упаковка для соцсетей)
└── summary.md         (автогенерируется координатором; ≤500 знаков для context budget будущих глав)
```

| Артефакт | Кто создаёт | Что внутри | Кто читает |
|----------|-------------|-----------|-----------|
| `spec.md` | `book-strategist` | ТЗ главы: цель, red thread keywords, ключевые примеры, структура (Pyramid: governing thought + 3 supports), что НЕ должно быть, параметры | автор (gate), писатель |
| `draft.md` | `book-writer` | Черновой текст главы по ТЗ | фактчекер, редактор |
| `factcheck.md` | `book-factchecker` | Отчёт о каждом утверждении: `[VERIFIED]`, `[CITED]`, `[ASSUMED]`, `[OUTDATED]`, `[SPECULATIVE]` | редактор, координатор (для loop verification) |
| `edited.md` | `book-editor` | Финальная отредактированная глава | автор (финальный gate), маркетолог, summary-генератор |
| `marketing.md` | `book-marketer` | Telegram-пост, Twitter-фрагменты, промпт обложки в Midjourney | автор |
| `summary.md` | автогенерация координатором | Сводка ≤500 знаков для context budget будущих глав | стратег и редактор будущих глав |

## Фаза 1. Стратег → `spec.md`

### Команда

```
> /book:plan-chapter <N>
```

Эта команда — **отдельная** от `/book:write-chapter <N>`. Её можно вызвать заранее, обсудить с автором, поправить руками, и только потом запустить полный цикл. Это специально: ТЗ — самая важная точка обсуждения; гейт автора после `spec.md` — обязательный (см. ниже).

### Вход

`book-strategist` получает (через `<files_to_read>`):

- `PROJECT.md` — видение книги.
- `ROADMAP.md` — план книги, контекст соседних глав.
- `red-thread-keywords.md` — сквозные термины-нити книги.
- `parameters.md` — фиксированные решения P-01, P-02, ... (например, «P-03: использовать только метрическую систему»).
- `chapters/<N-1>/summary.md` — сводка предыдущей главы.
- `agent-memory/strategist/MEMORY.md` — реестр уже использованных концепций / red thread keywords.
- `agent-guidelines/strategist/` — гайдлайны стратега для этой книги.

### Что делает стратег

1. Читает гайдлайны и контекст.
2. Прогоняет жанровый чек-лист (для научпопа — `popular-science-methodology` инжектируется через `skills:`).
3. Решает структуру главы по принципу Pyramid (governing thought + ≤3 supports).
4. Выбирает 2-3 ключевых примера, проверяя их против `agent-memory/strategist/MEMORY.md` (нет ли повтора с предыдущими главами).
5. Формирует чек-лист «что НЕ должно быть в главе» — foreshadowing для будущих глав, специально вынесенные темы.

### Выход — `spec.md`

```markdown
# Chapter 7: Кофейни Лондона: рассвет общественной мысли

## Цель главы
Показать, как кофейни Лондона XVII века стали первым «третьим местом»
европейской публичной сферы — между домом и церковью.

## Red thread keywords для этой главы
— «социальное пространство» (центральное в этой главе)
— «культурная адаптация» (англичане → одомашнили турецкий рецепт)

## Ключевые примеры
1. Кофейня «Pasqua Rosée» (1652) — первая в Лондоне; описание интерьера
2. «Penny universities» — за 1 пенни любой имел доступ к разговору
3. Lloyd's Coffee House — рождение страхового рынка

## Структура (Pyramid)
- Governing thought: «Кофе создал в Лондоне новую экологию диалога»
- Support 1: физическое пространство кофейни (что было до — paint pubs)
- Support 2: социальный разрез (кто приходил, что обсуждалось)
- Support 3: институциональное наследие (Lloyd's, Royal Society)

## Что в этой главе НЕ должно быть
— Истории распространения кофе по Европе (это глава 6)
— Французских кофеен XVIII века (это глава 8)
— Промышленной революции (часть III, после главы 12)

## Параметры
- target_length: 6500-8500 знаков
- voice: см. .book/context/voice-profile.md
- citation_style: footnote (P-04)
```

### Гейт автора

После `spec.md` срабатывает **обязательный гейт**:

```
✋ ТЗ главы 7 готово. Утверждаешь?
   (a) approve — переходим к написанию
   (b) revise — какие правки?
   (c) cancel — отложить
```

Это первый из двух гейтов цикла. Второй — после `marketing.md` (финальный обзор).

### Типичные проблемы и как чинить

| Проблема | Как чинить |
|----------|------------|
| Стратег предложил странный governing thought | Прервать, отредактировать `spec.md` руками или попросить переделать с уточнениями |
| Ключевые примеры пересекаются с уже использованными | Стратег это ловит автоматически (читает `agent-memory/strategist/MEMORY.md`); если пропустил — открыть файл и добавить вручную, перезапустить `/book:plan-chapter <N>` |
| ТЗ слишком объёмное (10+ supports) | Это нарушение принципа Pyramid. Сократить до ≤3 supports вручную или переформулировать `parameters.md` |

## Фаза 2. Писатель → `draft.md`

### Команда

Запускается автоматически после `spec.md` в составе `/book:write-chapter <N>`. Atomic-аналог — `/book:write-chapter:draft <N>` (только эта фаза, без последующих).

### Вход

`book-writer` получает:

- `chapters/<N>/spec.md` — ТЗ главы.
- `context/voice-profile.md` — голос автора.
- `agent-guidelines/writer/` — `voice-samples.md`, `forbidden-phrases.md`, `favorite-metaphors.md`.
- `agent-memory/writer/MEMORY.md` — реестр использованных примеров и метафор.
- `chapters/<N-1>/summary.md` — сводка предыдущей главы (для естественного перехода).

### Что делает писатель

1. **Voice gate.** Проверяет `voice-profile.md` — пуст или TBD-плейсхолдеры → возвращает диагностику `voice_pending` координатору, тот спрашивает автора (B1 / B2 / B3 — см. [`voice-management.md`](voice-management.md)). Без заполненного голоса писатель **не пишет ни строки** черновика. Это TOV-08 — структурная гарантия.
2. **Калибровка.** Пишет внутреннюю «настройку» — кратко, как звучит этот голос на этой теме. Не уходит в файл; стартовая разминка.
3. **Пишет блоками по 4000-6000 знаков с контрольными точками.** На каждом блоке — самопроверка: «не съехал ли я с голоса; не повторил ли пример».
4. **Hook anti-ai-cliche-lint** срабатывает после каждого `Write` или `Edit`. Если найдены клише уровня `block` (12 паттернов: sycophantic openings, kickbait, фейк-личный опыт) — exit code 2, blockирующий. Писатель видит вывод hook, переписывает блок, пишет снова. Если клише уровня `warn` (28: em-dash, англицизмы, signposting) — пишутся в комментарий, не блокируют. Уровень `info` (6 семантических) — для checklist'a.
5. **Двойной audit-pass.** После завершения драфта писатель проходит весь текст с явным вопросом «что выдаёт ИИ» и правит обнаруженное — это пассивный второй слой защиты от клише.
6. **Запись в реестр.** В конце — атомарно обновляет `agent-memory/writer/MEMORY.md` (использованные примеры, метафоры, voice notes).

### Выход

`chapters/<N>/draft.md` — черновой текст главы 6500-8500 знаков (для научпопа дефолт; параметризуется через `config.yaml`).

### Типичные проблемы и как чинить

| Проблема | Как чинить |
|----------|------------|
| Hook блокирует правомерную фразу (false positive) | Добавить исключение в `agent-guidelines/writer/forbidden-phrases.md` → `# Allowed (overrides default block)` |
| Текст звучит как ИИ, несмотря на hook | Запустить `/book:tune` — tuner проанализирует и предложит обобщённое правило. Или править голос: уточнить параметры в `voice-profile.md` (например, `emotional intensity: warm` → `restrained`) |
| Писатель повторяет пример из главы 3 | Открыть `agent-memory/writer/MEMORY.md`, проверить, что пример там зафиксирован. Если нет — добавить вручную, перезапустить `/book:write-chapter:draft <N>` |
| Voice gate сработал «не вовремя» | Выбрать B3 — агент сам предложит за 2-3 минуты. Или B2 (`/book:voice build` в отдельной сессии) |

## Фаза 3. Фактчекер → `factcheck.md`

### Команда

Запускается автоматически. Atomic — `/book:write-chapter:factcheck <N>`.

### Вход

`book-factchecker` получает:

- `chapters/<N>/draft.md` — черновик.
- `chapters/<N>/spec.md` — ТЗ (для понимания контекста).
- `agent-guidelines/factchecker/` — `trusted-sources.md`, `outdated-sources.md`, `claim-tags-rules.md`.
- `agent-memory/factchecker/MEMORY.md` — реестр source-IDs из предыдущих глав.

**`tools` фактчекера:** `Read`, `Write`, `WebSearch`, `WebFetch` (опционально MCP-серверы).
**`disallowedTools`:** `Edit` — структурная гарантия адверсариальной стойки. Фактчекер **не может** править текст; он только пишет отчёт. Если что-то нужно править — создаётся petлю верификации (см. ниже).

### Что делает фактчекер

1. Парсит `draft.md` на отдельные утверждения (фактологические).
2. По каждому делает поиск:
   - WebSearch для open-web фактов.
   - WebFetch для конкретных URL (если упомянуты в `trusted-sources.md`).
   - MCP-серверы — если подключены (например, MCP-PubMed для медицинских фактов).
3. Тэгирует каждое утверждение:
   - `[VERIFIED: <source>]` — нашёл подтверждение в trusted source.
   - `[CITED: <source>]` — есть ссылка, но требует ручного просмотра.
   - `[ASSUMED]` — не подтверждено, но и не опровергнуто; нужна проверка автором.
   - `[OUTDATED]` — найден более новый источник, противоречащий формулировке (это **BLOCKER**).
   - `[SPECULATIVE: <маркер>]` — нарративный момент, не фактологический (например, реконструкция, легенда).

4. Пишет `factcheck.md` со структурой:

```markdown
# Factcheck: Chapter 7

## Summary
- Total claims: 23
- VERIFIED: 14
- CITED: 5
- ASSUMED: 3
- OUTDATED: 0
- SPECULATIVE: 1

## Claims (по порядку появления в draft.md)

### Claim 1
> «Кофейня Pasqua Rosée открылась в 1652 году в Сент-Майклс-аллее»

[VERIFIED: britannica.com/topic/coffeehouse;
oldlondonpubs.com/2018/pasqua-rosee/]
Notes: Дата подтверждается в обоих источниках. Имя владельца — Pasqua Rosée
(не «Розе»; armenian, не итальянец, как иногда ошибочно).

### Claim 2
> «За 1 пенни любой посетитель имел право на доступ к любому разговору»

[CITED: Cowan, B. (2005) "The Social Life of Coffee: The Emergence of the
British Coffeehouse"]
Notes: «Penny universities» — устоявшийся термин в историографии XVIII в.
Точная цитата автора требует прояснения от писателя — где взято.

### Claim 3
> «Lloyd's Coffee House стал колыбелью страхового рынка»

[VERIFIED: lloyds.com/about-lloyds/history; encyclopedia.com/...]
Notes: ОК.

### Claim 7 (BLOCKER кандидат)
> «Royal Society была основана в кофейнях»

[OUTDATED] — это упрощённая формулировка. Royal Society была основана
в Gresham College (1660), кофейни были одним из сопутствующих культурных
феноменов, не местом основания.
RECOMMENDATION: переформулировать на «была частью той же интеллектуальной
экологии, что и кофейни».

(...)
```

5. Если есть `[OUTDATED]` или фактологически опасные `[ASSUMED]` — **status: revise-required** → инициирует loop verification.

### Loop verification (DEC-03)

Если `factcheck.md` отметил BLOCKER:

```
🤖 [book-coordinator] фактчекер обнаружил BLOCKER в claim 7.
   Запускаю writer revise-mode.
   ├─ Task(book-writer, ..., mode=revise, refs=[chapters/07/factcheck.md])
   ├─ Писатель правит формулировку
   └─ Re-check фактчекера → factcheck.md обновлён → status: pass.
```

Максимум 3 итерации loop'а. Если на 3-й всё ещё BLOCKER — координатор делает escalate-flow:

```
🤖 ⚠️ Loop max reached (3 итерации). Эскалирую.
✋ Что делать с claim 7?
   (a) принять как [SPECULATIVE] и пометить в тексте
   (b) удалить утверждение полностью
   (c) ручная правка writer'a с моим контекстом
   (d) отложить главу — нужны дополнительные источники
```

Каждое решение записывается в `REJECTIONS-LOG.md` для будущей работы tuner'а.

### Выход

`chapters/<N>/factcheck.md` со статусом `pass` (или escalate в редких случаях).

### Типичные проблемы и как чинить

| Проблема | Как чинить |
|----------|------------|
| Фактчекер не находит источник на простой факт | Проверить `agent-guidelines/factchecker/trusted-sources.md` — возможно, ваш домен не в списке. Добавить через `/book:guidelines factchecker` |
| Слишком много `[ASSUMED]` | Возможно, тема специфическая, и WebSearch не покрывает. Подключить релевантный MCP-сервер (например, MCP-PubMed для медицины) — конфигурация в `book-factchecker.md` → `mcpServers:` |
| Loop max reached | Прогнать decision (a/b/c/d) сознательно. Это нормально — некоторые утверждения нон-фикшна действительно требуют ручной проверки в библиотеке |

## Фаза 4. Редактор → `edited.md`

### Команда

Запускается автоматически. Atomic — `/book:write-chapter:edit <N>`.

### Вход

`book-editor` получает:

- `chapters/<N>/draft.md` — черновик.
- `chapters/<N>/factcheck.md` — отчёт о фактах.
- `chapters/<N-1>/edited.md` — предыдущая отредактированная глава (для cohesion).
- `agent-guidelines/editor/` — `cohesion-rules.md`, `author-deviations.md`.
- `agent-memory/editor/MEMORY.md` — реестр использованных sentence patterns.

### Что делает редактор

1. **4 уровня редактуры** (developmental → line → copy → proof):
   - Developmental: структура; «governing thought» точно ли держит главу?
   - Line: ритм абзацев, длина предложений, переходы.
   - Copy: типографика, тире, кавычки.
   - Proof: опечатки, рассогласования.
2. **Сокращает на ~10%** (King's −10% rule). Параметризуется через `config.yaml > editor.target_compression`.
3. **Двойной audit-pass анти-ИИ-клише** — после каждого `Edit` и в финале.
4. **Cohesion check.** Открывает `chapters/<N-1>/edited.md` и `<N-2>/edited.md` (через `summary.md` для context budget). Проверяет: переход естественный? Темы не повторяются? Нет противоречий?
5. **Если редактор изменил факты** — координатор автоматически перезапускает фактчекера re-check. Это второй loop в цикле, более редкий, но архитектурно важный.

### Выход

`chapters/<N>/edited.md` — финальная отредактированная глава. Это **тот текст, который пойдёт в книгу**.

### Типичные проблемы и как чинить

| Проблема | Как чинить |
|----------|------------|
| Редактор слишком агрессивно сокращает | Поправить `config.yaml > editor.target_compression: 0.05` (5% вместо 10%) |
| Cohesion с предыдущей главой плохой | Открыть `chapters/<N-1>/summary.md` — возможно, неполный. Регенерировать через `/book:write-chapter:edit <N-1>` (повторно прогон только редактора предыдущей главы) — он перепишет summary |
| Редактор поменял факт, фактчекер re-check fail | Loop инициируется автоматически. Если fail после 3 итераций → escalate-flow как в фазе 3 |

## Фаза 5. Маркетолог → `marketing.md`

### Команда

Запускается автоматически. Atomic — `/book:write-chapter:market <N>`.

### Вход

`book-marketer` получает:

- `chapters/<N>/edited.md` — финальная глава.
- `agent-guidelines/marketer/` — `brand-voice.md`, `telegram-tone.md`.
- `agent-memory/marketer/MEMORY.md` — реестр использованных визуальных образов и hook-формул.

> **Важно:** маркетинговые голоса (`brand-voice.md`, `telegram-tone.md`) **независимы** от базового `voice-profile.md`. Telegram-пост и обложка — другая риторика, чем глава книги. См. `TOV-10` в [`voice-management.md`](voice-management.md).

### Что делает маркетолог

1. **Telegram-пост** в 4-частной структуре: зацепка → развитие → ценность → call-to-action. Длина 800-1500 знаков.
2. **Промпт обложки** для Midjourney или DALL-E. Один крупный объект; не collage; не «карта мира с маршрутами»; 50-100 слов.
3. **3 фрагмента-цитаты** для X/Twitter, ВКонтакте, Threads. Длина 280-500 знаков каждый.
4. Проверяет против `agent-memory/marketer/MEMORY.md` — визуальный образ не повторяется (если в главе 1 обложка была «красная ягода крупно», то в главе 7 — что-то другое).

### Выход

`chapters/<N>/marketing.md` со всеми артефактами.

### Типичные проблемы и как чинить

| Проблема | Как чинить |
|----------|------------|
| Telegram-пост звучит банально | Поправить `agent-guidelines/marketer/telegram-tone.md` — уточнить тон, дать примеры |
| Промпт обложки повторяет визуальный образ | Маркетолог это ловит автоматически (читает `agent-memory/marketer/MEMORY.md`); если пропустил — добавить вручную |
| Маркетолог отключён, не нужен этот раздел | `workflow.md > chapter_loop.params.enable_marketer: false` — фаза пропускается, цикл завершается на `edited.md` |

## Гейты автора и петли верификации

### Два гейта автора

В стандартном пресете научпопа гейтов автора **только два**:

1. **После `spec.md`** — обязательный (`MC-03`). Автор подтверждает ТЗ, вносит правки, или отменяет цикл.
2. **После `marketing.md`** — финальный обзор. Автор смотрит готовую главу и упаковку, может править руками; если правит — координатор записывает в `REJECTIONS-LOG.md` (вход для будущего `/book:tune`).

Внутри пяти фаз — **полностью автономно**. Это сознательный архитектурный выбор: цель — снять с автора нагрузку «вручную переключать роли», характерную для работы в `claude.ai web`.

Гейты конфигурируются через `workflow.md > chapter_loop.gates`:

```yaml
gates:
  - spec        # default; обязательный
  - approval    # default; финальный обзор
  # - factcheck # opt-in; добавить, если хочешь видеть отчёт фактчекера до редактуры
  # - edited    # opt-in; добавить, если хочешь визировать перед маркетологом
```

### Петли верификации (loop verification)

Две автоматические петли:

1. **Writer ↔ Factchecker** (фаза 3, BLOCKER → revise → re-check, max 3 итерации, потом escalate).
2. **Editor ↔ Factchecker** (фаза 4, если редактор изменил факты, re-check, max 1 итерация на пару).

Эти петли — единственное место в цикле, где субагенты «общаются» не строго последовательно. Координатор оркестрирует, петли спрятаны внутри процедур; снаружи цикл выглядит как `spec → draft → factcheck → edited → marketing`.

## Atomic subcommands `/book:write-chapter:*`

Если одна фаза провалилась или нужна повторная только для части — есть атомарные подкоманды:

```
/book:write-chapter:draft <N>      # только писатель; перепишет draft.md
/book:write-chapter:factcheck <N>  # только фактчекер; перепишет factcheck.md
/book:write-chapter:edit <N>       # только редактор; перепишет edited.md
/book:write-chapter:market <N>     # только маркетолог; перепишет marketing.md
```

**Когда использовать:**

| Сценарий | Команда |
|----------|---------|
| Hook анти-клише не пропустил, переписал спорное место | `/book:write-chapter:draft <N>` |
| Подключил новый MCP-сервер, хочу прогнать фактчек заново | `/book:write-chapter:factcheck <N>` |
| Поправил `agent-guidelines/editor/cohesion-rules.md` | `/book:write-chapter:edit <N>` |
| Маркетолог отключён, потом включил — нужна marketing.md задним числом | `/book:write-chapter:market <N>` |
| Глава полностью устарела, переделать всё | `/book:write-chapter <N>` (полный цикл) |

**Идемпотентность.** Каждая atomic-команда — идемпотентна: можно вызвать сколько угодно раз, результат стабилен (если входы не менялись). Артефакты перезаписываются; бэкап предыдущих — в `chapters/<N>/.history/<timestamp>/` (если включен в `config.yaml > chapter.keep_history`).

**Не нарушай порядок.** Если запустишь `:edit` без обновлённого `factcheck.md`, редактор увидит старый отчёт — это не ошибка платформы, но логически неправильно. Координатор предупреждает:

```
⚠️ chapters/07/factcheck.md старее, чем chapters/07/draft.md (на 2 часа).
   Обычно после :draft нужен :factcheck.
   Продолжить :edit? (y/n)
```

## Recovery — что делать при ошибках

### Карта симптом → команда

| Симптом | Команда recovery |
|---------|------------------|
| Сессия упала посреди цикла | `/book:resume` — координатор читает `STATE.md` и `chapters/<N>/chapter-state.yaml`, возобновляет с прерванной фазы |
| `spec.md` устарел (изменил `parameters.md`) | `/book:plan-chapter <N>` — стратег переписывает spec; затем `/book:write-chapter <N>` |
| `draft.md` неудачный, всё переделать | `/book:write-chapter:draft <N>` — только фаза 2 |
| Фактчекер выдал FALSE BLOCKER (claim правильный) | Открыть `factcheck.md`, поправить тэг вручную (`[OUTDATED]` → `[VERIFIED: <ваш-источник>]`); затем `/book:write-chapter:edit <N>` |
| Cohesion с главой `<N-1>` плохой после правок | `/book:re-edit-chapter <N>` — переоткрывает редактуру с свежими сводками |
| Глава готова, но вы потом обновили `voice-profile.md` | `/book:re-edit-chapter <N>` — редактор пройдёт ещё раз с новым голосом |
| Координатор не помнит, на какой главе остановился | `/book:status` — читает `STATE.md`. `/book:next` — даёт умную подсказку (откуда продолжить, по `workflow.md`) |
| Hook сломался, exit code не возвращает | Проверить chmod: `ls -l .book/.hooks/anti-ai-cliche-lint.sh` — должен быть `755`. Если нет — `chmod +x .book/.hooks/anti-ai-cliche-lint.sh` |

### Чек-лист «глава не записывается»

1. `/book:doctor` — есть ли проблемы с инфраструктурой?
2. `chapters/<N>/chapter-state.yaml` — на какой фазе застряли?
3. `STATE.md` — что записано последним?
4. Если фаза-исполнитель — ошибка subagent'а: `/book:debug <slug>` — открывает persistent debug-сессию для расследования.

## Связь с workflow.md и параметризация

Микро-цикл главы — это секция `chapter_loop` в `.book/workflow.md`. На жанре «научпоп» дефолтный workflow выглядит так:

```yaml
chapter_loop:
  block: chapter-loop  # из каталога блоков
  params:
    enable_factchecker: true
    enable_marketer: true
    enable_skill_reviews: false  # дополнительные skill-режимы редактора (philosophical-review и т.д.)
    factcheck_max_iterations: 3
    target_length:
      min: 6500
      max: 8500
  gates:
    - spec
    - approval
```

Что можно настраивать:

| Параметр | Что меняет |
|----------|------------|
| `enable_marketer: false` | Цикл завершается на `edited.md`; `marketing.md` не создаётся |
| `enable_factchecker: false` | Пропускает фазу 3 (для жанров, где факт-чек не нужен — например, fiction в 0.2+) |
| `factcheck_max_iterations: 5` | Расширяет loop verification (для тем с очень спорными фактами) |
| `gates: [spec, factcheck, approval]` | Добавляет промежуточный gate после `factcheck.md` |
| `target_length.min`/`max` | Меняет дефолтный объём главы |

Полный список параметров блока — в `chapter-loop-block.md` каталога блоков (этап 7.1 проекта).

Жанровый скилл (`/book:research-genre <жанр>`) генерирует свой пресет workflow с другим набором параметров. Например, fiction-пресет в 0.2+ может выглядеть как:

```yaml
chapter_loop:
  params:
    enable_factchecker: false
    enable_consistency_check: true   # вместо фактчека — consistency check мира
    enable_marketer: false
```

Подробности — в [`customization.md`](customization.md).
